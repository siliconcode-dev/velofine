# CLAUDE.md — Velofine

This file is guidance for Claude Code when working in this repository. Read `Masterdoc.md` for full project context and `Build_plan.md` for the phased implementation plan before starting work. Always know which phase you're currently in.

## Project summary

Velofine is a standalone, launcher-level OptiFine-style patcher for Minecraft Java Edition 26.2, targeting Windows only. It is not a Fabric/NeoForge mod. It patches the game via a `-javaagent` at the bytecode level, installs as a custom launcher profile, and ships as a single branded `.exe` installer. Three independent engines: **LegacySupport** (ancient-hardware compatibility, especially a documented Intel HD 4000 rendering bug), **Optimus** (performance, OpenGL-focused), and **Utility** (OptiFine-parity QoL features + full shader pipeline support).

## How to work in this repo

- **Follow the phase you're in.** `Build_plan.md` is authoritative for sequencing. Don't build Phase 4 features while Phase 1's exit criteria are unmet. If a phase's exit criteria can't be verified (e.g. no access to the reference legacy hardware), say so explicitly rather than marking it done.
- **Phase 1 (patcher pipeline) and Phase 2 (Intel HD 4000 fix) are the highest-stakes phases.** Phase 1 is the architectural bet the whole project rests on. Phase 2 is a real, personally-verified bug affecting a real person (the project owner's friend) — treat correctness here as more important than speed.
- **No access to reference legacy hardware.** The project owner does not personally own the i3-3110M / Intel HD 4000 or i5-3470S / Intel HD Graphics 2500 test machines — validation of LegacySupport fixes depends on two friend/community testers, one per machine. When implementing LegacySupport features, write clear manual test/verification steps (what to check in the F3 debug screen, what log output confirms the fix engaged, etc.) so a non-developer tester can confirm results.
- **Keep engines decoupled from the start.** LegacySupport, Optimus, and Utility are independently buildable/runnable modules, and since Phase 5 each has its own master on/off toggle plus a real in-game config panel (`dev.velofine.core.gui`) — not one combined settings screen. `core` owns the config UI and its entry-point mixins so the panel stays reachable even if every engine is switched off.
- **Never let a feature silently degrade vanilla fidelity.** This applies especially to LegacySupport's memory-saving work (Phase 3) and Utility's texture/CTM features — "vanilla+" means vanilla behavior stays intact unless the user has opted into a change.

## Tech stack & conventions

- **Build tool:** Gradle, single monorepo with modules: `mcstubs` (since Phase 5 — shared, signature-only, `compileOnly`-everywhere Minecraft/Blaze3D stub types; see the Mixin section below for why this replaced Phase 4's per-engine `src/stubs/java`), `core` (shared utilities: config system, logging, GPU/hardware/memory/disk detection, `AgentContext`, the shared Mixin service/transformer plumbing every engine uses since Phase 4, and — since Phase 5 — the in-game config UI and its entry-point mixins), `legacysupport`, `optimus` (since Phase 5 also owns the adaptive performance governor, `optimus/.../governor`), `utility` (a real engine since Phase 5 — master toggle + safe-defaults policy; still zero QoL features, those are Phase 6), `launcher` (the self-attaching wrapper jar + installer CLI), `installer` (jpackage/Inno Setup packaging tooling, no Java source).
- **Language/runtime:** Java, targeting Java 25 (Minecraft 26.1+'s requirement). Confirm the exact minimum Java version Velofine itself requires vs. what it bundles for end users — these can differ.
- **Patching approach:** Runtime bytecode transformation via a self-attaching `-javaagent` (`launcher` module's `Main`/`VelofineAgent`, using the JDK Attach API + `-Djdk.attach.allowAttachSelf=true`, set via the generated profile's `javaArgs` — not a literal `-javaagent:` flag).
- **Mixin tooling decision (resolved Phase 1, implemented Phase 2, hoisted to `core` Phase 4):** SpongePowered Mixin (`org.spongepowered:mixin:0.8.7`), chosen over plain ASM on the strength of SpongeVanilla's precedent. A real custom `IMixinService` now exists (`core/.../mixin/VelofineMixinService.java` — moved here from `legacysupport` in Phase 4, see below) and is verified working against real vanilla 26.2 bytecode — see `legacysupport/src/test/java/.../diagnostic/VerifyMixinsHarness.java`, a manual diagnostic (not JUnit) that applies every engine's mixins directly to real class bytes extracted from the client jar and confirms via bytecode inspection (grew from 2 classes at Phase 2 to 6 across both engines by Phase 4, to 9 across four mixin configs by Phase 5). Key gotchas discovered building this (all now fixed, but relevant if this area breaks again):
  - `Mixins.addConfiguration(String)` (1-arg) passes a `null` fallback `MixinEnvironment` internally and NPEs in `MixinConfig.onLoad()`. Use the 2-arg overload (`addConfiguration(file, (IMixinConfigSource) null)`), which resolves `MixinEnvironment.getDefaultEnvironment()` properly.
  - `MixinServiceAbstract`'s default `getInitialPhase()` (`Phase.PREINIT`) doesn't match the `Phase.DEFAULT` environment `addConfiguration`'s fallback resolves to — two different `MixinEnvironment` objects, and `MixinConfig#select`'s reference-equality check silently drops the config (no error, mixins just never apply). `VelofineMixinService` overrides `getInitialPhase()` to return `Phase.DEFAULT` to fix this. Side effect: Mixin logs a scary-looking but harmless `ERROR: Initialising mixin subsystem after game pre-init phase!` — confirmed empirically this doesn't block anything for us (no FML-style staged pre-init phase to skip).
  - Mixin 0.8.7's `CompatibilityLevel` ceiling is `JAVA_21`, but its ASM-minor-version auto-detection (`Package.getImplementationVersion()`) can't read a version back from `launcher`'s shaded/merged jar, so levels needing an ASM minor-version check (anything above `JAVA_16`, which needs only ASM major version ≥9) spuriously fail even with real ASM 9.10.1 present. Every engine's `mixins.<engine>.json` uses `compatibilityLevel: JAVA_16` for this reason.
  - Mixin's own POM declares zero dependencies despite needing ASM (all 5 artifacts: asm, asm-commons, asm-tree, asm-util, asm-analysis) and Guava at runtime — wired explicitly in `core/build.gradle.kts` as `api(...)` (not `implementation`), since every engine's own mixin classes reference these types directly, not just `core`'s `MixinBridge`/`VelofineMixinService`. ASM 9.10.1 specifically, since real target classes are Java 25 bytecode (class file version 69, needs ASM 9.8+).
  - `mixins.<engine>.json` needs `-Dmixin.env.disableRefMap=true` (added to every generated profile's `javaArgs` by `ProfileInstaller`) since we don't use a refmap (real Mojang names, not SRG-obfuscated).
  - `@Mixin(targets = "string")` (not `@Mixin(RealClass.class)`) throughout, since we can't depend on Mojang's client jar at compile time (proprietary, not republishable). Real Minecraft types referenced in mixin method *signatures* are satisfied by hand-authored, signature-only stub classes — since Phase 5, in a single shared `mcstubs` module (`compileOnly` everywhere, never on any runtime configuration, so `shadowJar` can never bundle a fake `net.minecraft.*` class over the real one). This **reverses Phase 4's per-engine `src/stubs/java` decision**: that call made sense for a handful of duplicated types, but Phase 5's in-game config UI needs ~30 (GUI widget/screen/layout/narration types), and `core` (the UI), `optimus` (the governor) and `utility` all need the same ones — duplicating that three ways stopped being the cheaper option. Zero decompiled Mojang logic in any stub, just matching package/class/method names so `javac` can resolve them.
    - **Mixin 0.8.7's `@Shadow` does not walk the target's superclass hierarchy for fields** (confirmed against the real bytecode; tracked upstream as `SpongePowered/Mixin#284`, still open — `@Shadow` methods use `findMethodInHierarchy`, but `@Shadow` fields use a non-hierarchy `findField`). `VideoSettingsScreenMixin` needs `OptionsSubScreen.list` (declared on the target's superclass, not on `VideoSettingsScreen` itself) — the fix is to skip `@Shadow` for that field and instead cast `this` to a minimal `mcstubs` stub of the real ancestor class and read the field directly. This is legal at the real JVM level once Mixin merges the code into the real subclass's bytecode (protected-field-via-inheritance is ordinary Java), regardless of what visibility the fictitious stub declares — see `OptionsSubScreen`'s stub javadoc and `VideoSettingsScreenMixin` for the exact pattern if this need comes up again.
  - **Multiple engines sharing one transformer (Phase 4, stress-tested further in Phase 5):** `ServiceLoader`'s `META-INF/services` registrations for `IMixinService`/`IGlobalPropertyService` are global per-JVM — only one implementation of each can be active. `MixinBridge`, `VelofineMixinService`, `VelofinePropertyKey`, `VelofinePropertyService` therefore live in `core`, not any one engine, and `MixinBridge.install(Instrumentation)` is idempotent (guards against being called more than once) so each engine can independently call `MixinBootstrap.init()` + its own `Mixins.addConfiguration("mixins.<engine>.json", ...)` + `MixinBridge.install(...)` from its own `onAgentAttached()` without needing to coordinate ordering with other engines. Phase 5 added a fourth config (`mixins.velofine-core.json`, installed by the new `CoreEngine`, always first in `VelofineAgent.init` since the config UI must stay reachable even with every other engine disabled) and, for the first time, two *different* configs independently targeting the *same* real class (`net.minecraft.client.Minecraft` — Optimus's tick-profiler/governor hook and core's config-keybind poll both inject into `tick()`). `VerifyMixinsHarness` confirms both engines' handler methods survive in the one transformed class, and hand-disassembly confirms they run in the expected order (`HEAD` injection first, then the two `RETURN` injections in registration order) — the shared-transformer design holds up under a second independent injector on the same method, not just two configs on disjoint classes.
- **Installer packaging:** `jpackage --type app-image` (bundles a Java 25 runtime via jlink) → **Inno Setup 6.6+** for the final Windows `.exe` (`installer/installer.iss`, run via the `:installer:jpackageAppImage`/`:installer:innoSetupCompile` Gradle tasks). UI direction: **black / white / red palette, brutalist design language** — Inno Setup 6.6+ supports this natively (`WizardStyle=dark`, `WizardBackColor`, custom `WizardImageFile`/`WizardSmallImageFile`), no hacky workarounds needed. Apply consistently across installer screens and any in-game Velofine UI, not just the installer — the in-game config UI (`dev.velofine.core.gui`, Phase 5) is the first place this direction has actually been implemented: fully custom-drawn (no vanilla sprites), same black/white/red palette. Installs per-user to `{localappdata}\Velofine` — no admin/UAC required. Source logo art drops into `assets/`; the actual consumed, pre-sized files live in `installer/branding/` (currently placeholder art — see `assets/README.md`).
- **License:** LGPL for the whole project. Apply LGPL license headers consistently. If/when Phase 7 (shaders) adapts components from Iris (also LGPL), keep attribution and licensing clean — do not silently vendor code without proper LGPL compliance (source availability, license notices).
- **No telemetry, ever.** No crash reporting, no analytics, opt-in or otherwise. Do not add any network call that phones home data about the user's system beyond the explicitly-designed in-app updater checking for new releases.
- **No code signing for v1.** Windows SmartScreen warnings on the unsigned installer/updater are expected and accepted — don't try to work around this with anything other than clear README/installer messaging.

## LegacySupport: real findings (Phase 2, grounded in the real 26.2.jar via javap)

- `com.mojang.blaze3d.opengl.GlBackend.setWindowHints()` is the exact, isolated method requesting the GL context. Vanilla requests **OpenGL 3.3, Core Profile, Forward-Compatible**. `GlBackendMixin` `@Overwrite`s it: on a detected fix profile, requests 3.3 **Compatibility** Profile with forward-compat dropped instead (same version, superset of core, shouldn't break anything core-profile-only code does).
- `com.mojang.blaze3d.opengl.GlDevice.compileShader(...)` calls `ShaderSource.get(Identifier, ShaderType)` to obtain GLSL source text — the one place to intercept for the shader `mix()` patch. `GlDeviceMixin` `@Redirect`s that single call.
- `GpuDetector` (`core` module) identifies Intel Gen7 (HD Graphics 4000/2500) via `Get-CimInstance Win32_VideoController` (PowerShell/WMI) adapter-name matching — not Sodium's native D3DKMT/`ig7icd*.dll` approach, which needs JNA/native calls we deliberately avoided for a Windows-only v1.
- Both fixes are **hypotheses grounded in real research** (OptiFine's historical mirror-image Intel GL-profile issue; an Intel Community forum thread on `mix()` constant-folding bugs), not confirmed against the actual reference hardware — nobody on this project has access to it. Verified so far: the Mixin pipeline genuinely transforms the real target classes correctly (see `VerifyMixinsHarness`) and the generated profile launches clean on unaffected hardware. **Not yet verified:** whether these fixes actually resolve the invisible-portals/lava/water bug on the i3-3110M/i5-3470S reference machines — that's the real acceptance test per Build_plan, pending the two testers.

## LegacySupport: generalized fix system + Phase 3 findings (grounded in the real 26.2.jar via javap)

- The Phase 2 pattern of hand-written boolean methods on `LegacySupportEngine` branching on a single flat `GpuInfo.FixProfile` enum has been replaced with a composite model in `core`'s new `dev.velofine.core.hardware` package: `HardwareProfile` (GPU + `MemoryInfo` + `DiskInfo`, each with its own PowerShell/WMI-based detector following `GpuDetector`'s exact shape) resolves via `FixProfileRules` (a short list of independent, additive `(predicate, fixes)` rules) to a `Set<Fix>`. Every mixin now checks `LegacySupportEngine.isFixActive(Fix.X)` instead of a bespoke boolean getter — adding a new hardware class going forward means adding one `FixProfileRules` entry, not touching call sites. The dev-testing hook is now `-Dvelofine.legacysupport.forceFixes=<comma-separated Fix names>` (replaces Phase 2's `forceProfile`).
- `MemoryDetector` classifies ≤6GB total physical RAM as "low-memory" (headroom above the documented 4GB reference machines, since real 4GB sticks report somewhat under 4×1024³ bytes). `DiskDetector` resolves the game directory's drive letter → partition → disk number → `Get-PhysicalDisk`'s `MediaType` to detect a rotational HDD; the game directory itself is threaded through as a new `-Dvelofine.gameDir` system property, set by `Main.captureGameDir()` from the real `--gameDir` launch arg *before* self-attaching (same JVM, so the property is visible to the agent) — not baked into the generated profile JSON, since the actual directory is only known at each real launch, not at profile-generation time.
- `net.minecraft.server.level.ChunkMap.saveChunksEagerly(BooleanSupplier)` throttles eager dirty-chunk saves via a real vanilla constant (`CHUNK_SAVED_EAGERLY_PER_TICK`, confirmed `ConstantValue: int 20`, inlined by javac at its one use site in this method with no other colliding `20` literal). `ChunkMapMixin` `@ModifyConstant`s it down to 6 when `IO_STALL_SMOOTHING` is active, reducing how many saves get queued against the same single-threaded IO executor that also services chunk loads on a rotational disk.
  - **Investigated and deliberately rejected:** directly reordering `IOWorker`'s load/save priority (the originally-planned approach). javap showed both `store(...)` and `loadAsync(...)` funnel through one private `submitTask` method with `IOWorker.Priority.FOREGROUND` hardcoded via a `getstatic` *inside* `submitTask` itself — not passed by the caller — so there's no caller-side seam to redirect safely. The only way to give saves a different priority would be reimplementing `submitTask`'s internal `scheduleWithResult` callback wiring by referencing its synthetic lambda method (`lambda$submitTask$0`) by name — an unstable javac implementation detail, not a real API, and a bad foundation for a shipped correctness-sensitive feature (this is chunk-save code; a wiring mistake risks corrupting player worlds). `ChunkMap`'s named, single-purpose constant was the safer real lever.
- `net.minecraft.client.Options`'s constructor sets first-run defaults for `renderDistance`/`simulationDistance`/`entityDistanceScaling`/`mipmapLevels`/`particles` (all confirmed real `OptionInstance<T>` fields). `OptionsMixin` lowers these when `MEMORY_SAVING_DEFAULTS` is active, via `@ModifyConstant`/`@Redirect` scoped with Mixin's `@Slice` between each option's own translation-key string constant (e.g. `"options.mipmapLevels"`) and its field assignment — necessary because the constructor is one ~5000-instruction method covering every video setting, with several colliding literal values (e.g. `12` is the default for *both* render and simulation distance; `4` appears twice just for mipmapLevels' own range-max and default). Slice-bounding by stable, named anchors (rather than a raw global ordinal) means an unrelated constant added elsewhere in a future Minecraft version can't silently shift which value gets modified — Mixin fails loudly at apply time if a slice boundary goes missing instead. Verified via `VerifyMixinsHarness` (extended for `ChunkMap`/`Options`) that all five injections land on the intended instruction — confirmed by hand for the two trickiest cases (`mipmapLevels`' ordinal disambiguation, `particles`' field redirect) by disassembling the transformed class and checking the injected call sits exactly at the default-value slot, not the range-bound slot.
  - This only ever changes what a *fresh* install starts at: vanilla's own `options.txt` load (immediately after construction) overwrites any of these fields if the file already exists, so no explicit "does options.txt exist" check was needed in the mixin — vanilla's load order provides that gate for free.
  - Chosen low-memory defaults: render/simulation distance 6, entity distance scaling 0.5 (its range minimum), mipmap levels 0, particles `DECREASED` (not `MINIMAL` — a conservative starting point per the project owner's explicit choice this phase).
- True dynamic texture-atlas streaming (load/evict on demand) was explicitly scoped out of Phase 3 — too risky to build and validate without reference hardware. The mipmap-level default above is the only texture-memory lever shipped this phase.
- Like Phase 2, these are **hypotheses grounded in real research and verified-correct bytecode transforms**, not yet confirmed to reduce stutter/memory footprint on the actual i3-3110M/i5-3470S reference machines — pending the two testers, same as Phase 2.

## Optimus: real findings (Phase 4, grounded in the real 26.2.jar via javap)

- **Vanilla 26.2 already ships a modern, fully-async chunk-building and world-gen pipeline** — a real difference from the pre-1.17 era Sodium/C2ME/Lithium originally targeted. `net.minecraft.util.Util.makeExecutor(String)` builds a shared `ForkJoinPool` sized via `Mth.clamp(availableProcessors() - 1, 1, getMaxThreads())`, where `getMaxThreads()` reads a real, already-supported `-Dmax.bg.threads=<1-255>` system property (default 255, i.e. uncapped-by-property). This one pool (`Util.backgroundExecutor()`) is what `SectionRenderDispatcher` (chunk mesh building) is constructed with, and `ChunkTaskDispatcher`/world-gen dispatch draws from the same shared background-executor infrastructure — so one explicit thread-count decision benefits chunk building, world gen, and IO simultaneously. Vanilla was *already* 2-core-aware by formula, just implicit; Optimus's contribution is making it explicit and Optimus-owned: `OptimusEngine.applyThreadPoolTuning()` computes `max(1, availableProcessors() - 1)` and sets `-Dmax.bg.threads` via `System.setProperty` in `Main.main()`, before self-attach (same "same-JVM, set-before-vanilla-classes-load" ordering Phase 3 proved safe for `velofine.gameDir`) — **no mixin, no bytecode patching** for this item.
- This finding substantially satisfies Build_plan's "chunk mesh caching and threaded/multithreaded chunk building" and "multithreaded world generation" bullets without reimplementing either — both already exist natively in 26.2. `SectionTaskDynamicQueue.MAX_RECOMPILE_QUOTA = 2` (per-frame chunk-recompile dequeue cap) is a real, named, already-conservative constant in the same vein, left untouched pending real profiling data (see `TickProfiler` below) rather than guessed at.
- `net.minecraft.world.entity.Mob.serverAiStep()` (confirmed real method) already staggers full goal-selector re-evaluation to every `UPDATE_GOAL_SELECTOR_EVERY_N_TICKS` (confirmed `ConstantValue: int 2`) ticks per entity, offset by `getId()` so mobs don't all re-evaluate on the same tick; in between, only currently-running goals continue (`tickRunningGoals(false)`, cheaper than the full `GoalSelector.tick()`). `MobMixin` `@ModifyConstant`s the inlined literal `2` (confirmed the only occurrence in the ~270-instruction method body, hand-verified by disassembling the transformed class) up to `3`, a modest, Lithium-precedented (reduced goal-selector re-evaluation frequency) throttle. Unconditional — Optimus has no `Fix`/`HardwareProfile` gating (see below), so this is a plain constant swap with no runtime branch.
- `net.minecraft.client.Minecraft.tick()` (confirmed real, single-overload method) is vanilla's one client-tick entry point. `MinecraftMixin` `@Inject`s at `HEAD`/`RETURN` (pure side-effect injection, can't alter tick behavior regardless of what the injected code does — the lowest-risk mixin category) to drive `optimus/.../profiling/TickProfiler`, a deliberately simple `System.nanoTime()` rolling-window sampler (not JFR — no reference-hardware data yet to justify a heavier framework) that logs min/avg/max tick time every 100 ticks. Exists to give testers and future tuning (this phase's own throttle constants, Phase 5's adaptive governor) real numbers instead of guesses.
- **Optimus's optimizations are unconditional** (explicit project-owner decision, Phase 4): they apply on every install regardless of detected hardware, matching how Sodium/Lithium/C2ME actually behave — unlike LegacySupport's `Fix`/`HardwareProfile` gating. No per-engine toggle exists yet (Phase 5); until then this means "on by default."
- Like Phases 2/3, whether the goal-selector throttle and explicit thread-pool sizing produce a measurable, player-noticeable improvement on the actual i3-3110M/i5-3470S reference machines is **unconfirmed** — verified so far only as correct, real bytecode transforms (via `VerifyMixinsHarness`, hand-disassembly-checked) and a clean local install/launch round-trip, same tester-dependent framing as every prior phase's hardware-specific claims.

## Phase 5: adaptive Optimus + config UI (grounded in the real 26.2.jar via javap)

- **Config system, finally real.** `dev.velofine.core.config.VelofineConfig` is a plain Gson-serialized POJO tree persisted at `<gameDir>/velofine/config.json` by `ConfigManager` (write-then-atomic-rename; a malformed file is quarantined to `config.json.bak` and replaced with defaults rather than crashing the launch — both paths verified against the real Legacy Launcher game directory, not just synthetic fixtures). Deliberately **not** under `libraries/dev/velofine`, since `ProfileInstaller.uninstall()` deletes that tree recursively and a user's settings should survive a reinstall. `ConfigManager.load(gameDir)` runs in `Main.main()` right after `captureGameDir`, before self-attach, so it's already populated by the time every engine's `onAgentAttached` runs in the same JVM.
- **`Tri` (`AUTO`/`ON`/`OFF`) is the override model for LegacySupport's per-`Fix` toggles**, not a plain boolean — `AUTO` means "keep letting `FixProfileRules` decide," so a user override never has to fight hardware detection or go stale if detection logic improves later. `LegacySupportEngine.resolveFixes()` layers it as: `-Dvelofine.legacysupport.forceFixes` (dev-only, replaces the whole set) → per-fix `Tri` override on top of `FixProfileRules.resolve()` → nothing (empty set, mixins never install).
- **`HardwareProfile` detection hoisted from `LegacySupportEngine` to `core`'s new `HardwareProfiles`** (detect-once-and-cache, same three PowerShell/WMI detectors as before). This was a real coupling problem before Phase 5: Optimus's governor default and Utility's safe-defaults policy both need to know if the hardware is "weak," and neither engine should have to depend on `legacysupport` to ask. `HardwareProfiles.isWeakHardware()` = old-Intel-class GPU **or** ≤6GB RAM **or** rotational game-directory disk (a union, since the two reference machines differ from each other — the i3-3110M is an HDD laptop, the i5-3470S an SSD desktop).
- **Every engine now has a master on/off toggle gating whether its mixin config is even installed** (`engines.legacySupport`/`optimus`/`utility` in config, read at `onAgentAttached` time — a restart-required toggle, since it's evaluated once at agent attach). `CoreEngine`'s own mixin config is the one exception with no gate: the config UI must stay reachable even when every other engine is off, or a user who disables all three would lock themselves out of the only place to turn them back on.
- **The adaptive performance governor (`optimus/.../governor`) needs zero mixins to actuate.** Confirmed via javap: `OptionInstance.set(T)` validates the value and, if it actually changed and the game is running, fires the option's own `ValueUpdateListener` — and `Options.renderDistance` is constructed *with* one, which is what triggers vanilla's own chunk-graph rebuild and server view-distance packet. `PerformanceGovernor.onClientTick()` (driven by the existing `MinecraftMixin` tick hook, alongside `TickProfiler`) just calls `mc.options.renderDistance().set(n)` directly. Tuning follows DRD (Dynamic Render Distance), the closest actively-maintained prior art: 5-second rolling FPS average, evaluate every 5s, descend fast (−2) and climb slow (+1), 10s cooldown, never above the user's own render distance (tracked as `governor.baselineRenderDistance` in config — re-adopted from the live value whenever it differs from what the governor itself last set, so a manual change in Video Settings becomes the new ceiling instead of being silently overwritten). Default: `ADAPTIVE` only when `HardwareProfiles.isWeakHardware()` at first config creation, `OFF` everywhere else — the governor must never move a modern-hardware user's render distance without them asking.
- **In-game config UI is fully custom-drawn ("brutalist"), not a vanilla `OptionsSubScreen` subclass** (an explicit project-owner choice this phase) — flat black/white/red panels, no vanilla sprites, structured like Sodium's video-settings screen (left tab rail, one page per engine, hover-driven description box, staged UNDO/APPLY so half-edited settings never leak into the running game). Confirmed via javap that this only costs the drawing: `AbstractWidget` has exactly two abstract methods, so custom widgets still inherit all of vanilla's hover/focus/tab-order/click machinery, and `Screen` itself declares none, needing only `init()` + `extractRenderState(GuiGraphicsExtractor,...)`. 26.2 renders GUIs through a render-state *extraction* pass (`Renderable.extractRenderState`), not the older immediate-mode `render(GuiGraphics,...)` — every custom draw call in `dev.velofine.core.gui` targets `GuiGraphicsExtractor`.
- **Three entry points, all confirmed via `VerifyMixinsHarness` + hand-disassembly against the real 26.2 jar:**
  - Video Settings: `@Inject` at `RETURN` of `VideoSettingsScreen.addOptions()`, `list.addBig(...)` — scrolls with the list, cannot overlap a vanilla widget, no layout math.

### Phase 7.5: composite/deferred/final pipeline — implemented and harness-verified

- **Real integration mechanism confirmed via `-c` disassembly of `GameRenderer.render(...)`**: vanilla's own built-in post effects (blur, the configurable single-slot `postEffectId` Phase 6's AA already uses) go through `ShaderManager.getPostChain(Identifier, Set<Identifier>)` then `postChain.process(mainRenderTarget, resourcePool)`. `ShaderManager.getPostChain` only resolves configs from real, static resource-pack assets (confirmed via its full method list - `prepare`/`apply`/`loadPostChain` all read from a `ResourceManager` reload pass), which a shader pack's dynamically-built `PostChainConfig` is not - so `dev.velofine.shaders.pipeline.CompositeRenderer` bypasses it and calls `PostChain.load(...)` directly, reusing `ShaderManager`'s own dedicated `postChainProjection`/`postChainProjectionMatrixBuffer` fields (exposed via a new `ShaderManagerAccessor` `@Accessor` mixin) rather than the level's real 3D projection - correct here since composite/deferred/final passes are full-screen-quad operations, not 3D geometry.
- **`CompositePipelineBuilder`** constructs a real `PostChainConfig` from a pack's `deferred`/`deferred1-15`/`composite`/`composite1-15`/`final` files (both `.vsh` and `.fsh` required - no substitute for OptiFine's implicit default vertex shader, since that would mean vendoring Mojang's own builtin GLSL). `DrawBuffersDirective` parses `DRAWBUFFERS`/`RENDERTARGETS` comments; `colortexN` sampler declarations are auto-detected as pass inputs. **Real fix caught during this work**: the `final` program's output must target `PostChain.MAIN_TARGET_ID` (the real screen), not another `colortexN` buffer, or the whole chain's result never reaches the display - and if a pack has no explicit `final` program, the *last* composite/deferred pass found is now retargeted to `MAIN_TARGET_ID` instead, matching OptiFine's own implicit behavior.
- **Two real bugs found and fixed via `VerifyMixinsHarness`, not just trusted from compilation**:
  1. `VelofineAgent` never called `ConfigManager.load(...)` itself - only `Main.main()` did, before self-attaching. A literal `-javaagent:` attachment (this class's own documented manual-testing path, and how the harness itself exercises the real agent) skips `Main.main()` entirely, so every engine silently saw in-memory config defaults regardless of a real `config.json` on disk. Fixed by having `VelofineAgent.init()` also call `ConfigManager.load()` using `-Dvelofine.gameDir` if set - harmless in the normal flow (redundant re-read of the same file), essential for the javaagent-flag path.
  2. Mixin's `@Accessor` requires the accessor method's return type to match the target field's *exact declared type*, not a widened supertype/interface - `GameRendererAccessor.velofine$getResourcePool()` typed to `GraphicsResourceAllocator` (the interface `GameRenderer.resourcePool`'s real type `CrossFrameResourcePool` implements) threw `InvalidAccessorException` at Mixin apply time. Fixed by stubbing `CrossFrameResourcePool` itself and typing the accessor to it directly; ordinary Java polymorphism handles the widening when the value reaches `PostChain.process`, which only needs the interface.
- **Loading is deliberately lazy**: `ShaderPipelineState.activate()` (agent-attach time, before `Minecraft`/`GameRenderer`/`ShaderManager` exist) only builds the `PostChainConfig` and hands it to `CompositeRenderer.onPackActivated()`, which stores it as *pending*; the real `PostChain.load()` call happens on the first `CompositeRenderMixin`-driven `processFrame()` call, by which point real instances are guaranteed to exist.
- **Verified via `VerifyMixinsHarness`**: all 18 markers pass (13 pre-Phase-7 + `core.mixin.GlDeviceMixin`'s `velofine$resolveShaderSource` + `ShaderManagerAccessor`'s two accessors + `GameRendererAccessor`'s one + `CompositeRenderMixin`'s `velofine$processCompositePipeline`), confirmed against real transformed bytecode of `GlDevice`, `GameRenderer`, and `ShaderManager`. Required a scratch `velofine/config.json` (`utility.shader.enabled: true`, `selectedPackName` set) and a matching `shaderpacks/<name>/shaders/` folder, since the harness's own bytecode-transform verification needed a real config path to exercise `ShaderEngine`'s mixin-install gate - not committed to the repo, a throwaway test fixture.
- **Still unverified in a real running game** (the harness confirms bytecode transforms are correct, not runtime rendering behavior) - `CompositeRenderer`'s own class javadoc flags this explicitly. Real launch testing is the next step once the project owner is ready.
- **Phase 7.6 (shadow pass) is explicitly skipped for v1**, per the project owner's decision - not a blocker: shadow integration is additive (a second render pass into `shadowtex`/`shadowcolor` targets, recognized as extra sampler names in `CompositePipelineBuilder`'s existing input-scan pattern) and needs no rework of anything built so far. A composite/deferred pass that reads `shadowtex`/`shadowcolor` without Velofine providing them won't crash (unbound GL samplers read as black/default, not a link failure) - it just renders without dynamic shadows, consistent with the already-narrower v1 GLSL-compatibility scope below.

### Phase 7.7: shader-pack options UI — implemented

- **Real option discovery, not just a stub `OptionSet`**: `dev.velofine.shaders.format.option.OptionDiscovery` scans every `.vsh`/`.fsh` directly under a pack's `shaders/` for OptiFine-style annotated `#define NAME value // comment [allowed values]` lines, using the same `StringOption.create`/bracket-parsing convention adapted from Iris in 7.2. Per-file only, not across a real `#include` graph (same documented scope cut as before) - revisit if a validation pack's real options live in included files.
- **A real, previously-silent bug fixed while wiring this up**: `ShaderPipelineState.activate()` was calling `ShaderPack.load(name, root, List.of())` - an always-empty list - meaning a user's persisted option overrides (`VelofineConfig.ShaderSection.packOptions`) never actually reached `shaders.properties` preprocessing, only the (previously nonexistent) options screen would have shown them. Fixed by reordering `ShaderPack.load()` to run option discovery *first*, resolve the enabled-boolean set against the user's overrides, *then* preprocess `shaders.properties` - since which booleans exist is only knowable after scanning the pack's GLSL, but preprocessing needs the resolved set.
- **Cross-module GUI architecture**: `core` owns the whole config UI (including `UtilityPage`) but cannot depend on `shaders` (wrong direction - `shaders` already depends on `core`). Resolved with the same pattern `ShaderSourceInterceptors` already established for the identical problem: `core.shader.ShaderPackBrowser`/`ShaderPackBrowserRegistry` (a plain-data interface + static holder in `core`) is implemented by `dev.velofine.shaders.ShaderPackBrowserImpl` and registered from `ShaderEngine` - `core`'s GUI code only ever sees flattened `ShaderPackOptionInfo` records, never `shaders`' own `BooleanOption`/`StringOption`/`OptionSet` types.
- **The browser registers unconditionally**, before `ShaderEngine`'s enabled/pack-selected checks - pack *discovery* (listing `shaderpacks/`) is cheap directory I/O and needs to work even when the feature is off, so a user can see what's available before turning it on; only pack *activation* (parsing GLSL, building the composite pipeline) stays gated.
- **New GUI widgets** (`dev.velofine.core.gui`): `NavigateRow` (an `OptionRow` whose `activate()` opens a sub-screen instead of cycling a value - both click-halves trigger the same action) and `ShaderOptionsScreen` (a plain, non-tabbed screen listing the active pack's discovered options, reusing `CycleRow` for both boolean and string/enum options rather than a new row type - confirms Phase 6's finding that the existing row vocabulary stretches further than expected holds again here). Deliberately **not** staged behind UNDO/APPLY like the main config screen - every option edit is already a "reload the pack" operation (`ShaderPackBrowser.setOptionValue` re-activates immediately), so applying on click is consistent with the live-on-click precedent `UtilityPage`'s AA/mipmap/Vsync rows already set, not a special case.
- **A real, necessary framework change**: `ConfigPage.buildRows(...)` gained a third `Screen screen` parameter (the config screen itself), threaded through all four page implementations and `VelofineConfigScreen`'s call site. Needed because `NavigateRow`'s "open `ShaderOptionsScreen`, then return to where you were" requires a real parent-screen reference, and confirmed via javap that `Minecraft` has no plain `Screen`-typed field to read the current screen from ambiently - a small, mechanical, low-risk signature change (the other three pages simply ignore the new parameter), not touched blindly.
- **Verified via a full `VerifyMixinsHarness` re-run after all Phase 7 changes**: still 18/18 markers pass, confirming the `ConfigPage`/`UtilityPage` changes didn't regress the GUI entry-point mixins (`VideoSettingsScreenMixin`/`PauseScreenMixin`/`MinecraftKeybindMixin`) or anything else.
- **Not testable by the harness**: `ShaderOptionsScreen`/`UtilityPage`'s new rows are plain Java GUI code, not mixins - the harness confirms bytecode transforms, not that the screen actually renders/behaves correctly. Real in-game verification (opening the Utility page, picking a pack, opening its options screen, editing a value) is still pending, same caveat as 7.4/7.5.

### Phase 7 checkpoint: real GLSL-compatibility gap, and the resulting v1 scope decision

- **`GlProgram.link(GlShaderModule, GlShaderModule, VertexFormat[], String)` (confirmed via javap) binds vertex attributes and uniforms by name**, not by a rigid structural contract - so raw shader-pack GLSL only actually runs if its `in`/`uniform` declarations use the exact names the real pipeline's `VertexFormat`/uniform system expects. Real OptiFine/Iris-format packs are authored against OptiFine's own legacy naming convention (`gl_Vertex`, `gl_MultiTexCoord0`, `gl_Normal`, `gl_ModelViewMatrix`, GLSL 120-150-era `attribute`/`varying`), which does **not** match vanilla 26.2's real names.
- **Iris's own translation layer for this (`pipeline/transform/TransformPatcher.java` and its ~10 `transformer/` visitor classes - `VanillaTransformer`, `CompatibilityTransformer`, `LayoutTransformer`, `TextureTransformer`, etc.) is built entirely on `glsl-transformer`** (full ANTLR-based GLSL AST parsing/transformation) - confirmed by reading the real file, not inferred. This is precisely the AGPL-3.0 dependency the project owner already declined to take on (see the license-resolution notes above) - a from-scratch equivalent is a genuinely large, standalone undertaking (parsing, AST manipulation, per-transformer-pass logic), not something addressable with a quick text-substitution shim.
- **Explicit project-owner decision on this checkpoint: narrow v1's compatibility target rather than build any legacy-GLSL translation layer.** A Velofine-compatible v1 shader pack must be authored directly against vanilla 26.2's real attribute/uniform names, not OptiFine's traditional convention. `ShaderProgramLoader` stays a pure pass-through (plus `jcpp` preprocessing) - no rewriting.
- **Real naming convention, confirmed by extracting actual vanilla shader assets from the 26.2 jar** (`assets/minecraft/shaders/core/{terrain,entity}.vsh` - read only to document the attribute/uniform *names* as a compatibility target, not vendored into the repo; the shader logic itself is proprietary Mojang code and stays out): vanilla's own shaders are already clean modern GLSL 330 core (`in`/`out`, no legacy builtins) - so "modern GLSL" as a target is not a Velofine invention, it's what vanilla already does. Per-pipeline vertex attributes differ by draw category and must match exactly:
  - `SOLID_TERRAIN`/`CUTOUT_TERRAIN`/`TRANSLUCENT_TERRAIN` (`gbuffers_terrain`/`gbuffers_water`): `in vec3 Position; in vec4 Color; in vec2 UV0; in ivec2 UV2;` (no `Normal`, no `UV1`).
  - `ENTITY_*` (`gbuffers_entities`): `in vec3 Position; in vec4 Color; in vec2 UV0; in ivec2 UV1; in ivec2 UV2; in vec3 Normal;` - a superset of terrain's (adds overlay UV1 and Normal).
  - Common real uniform names seen across both: `ModelViewMat`, `ProjMat`, `ChunkPosition`, `CameraBlockPos`, `CameraOffset`, `FogColor`, `ChunkVisibility`, `Light0_Direction`/`Light1_Direction`. Vanilla's own shaders reach these via `#moj_import <minecraft:....glsl>` (Mojang's own shared-GLSL-snippet mechanism) rather than redeclaring them per file - a shader pack substituted through Velofine's interceptor does not need `#moj_import` itself (the interceptor replaces the *entire* source text, so nothing downstream re-resolves Mojang's imports for pack-provided source), it just needs to declare these as plain `uniform` variables directly if it wants to read them.
  - Vanilla also uses its own `#ifdef`-style conditional compilation extensively (`PER_FACE_LIGHTING`, `EMISSIVE`, `NO_OVERLAY`, etc., driven by each `RenderPipeline`'s own `getShaderDefines()`) - confirming the `RenderPipeline`/`ShaderDefines` system is already define-driven and modular on vanilla's side, independent of anything Phase 7 adds.
- **Real, honest tension with `Build_plan.md`'s Phase 7 exit criteria** ("A sample of popular OptiFine- and Iris-format shader packs load and render correctly with no code changes required from the user"): this narrowed scope means genuine published OptiFine/Iris-format packs (BSL, Complementary, etc., as they actually exist) will **not** satisfy v1's compatibility requirement without being manually rewritten to target vanilla's real names - the exit criteria as originally written is not achievable under this scope decision. Flagged here rather than silently reinterpreted; needs an explicit revisit (either accepting a narrower v1 validation target - a hand-authored "modern GLSL" test pack instead of a real downloaded one - or reopening the AGPL-dependency question later) once the rest of the pipeline (7.4 custom framebuffers, 7.5 composite/deferred, 7.6 shadow) is far enough along to know how much further investment is worth it.

# CLAUDE.md — Velofine 1.5 Update

This is a focused addendum for the **v1.5 update work** on top of the existing shipped Velofine v1 codebase. Read `Masterdoc_v1.5.md` for full context and `Build_plan_v1.5.md` for phase sequencing before starting. If a repo-root `CLAUDE.md` already exists from v1, treat this as the currently-active supplement while v1.5 work is in progress — don't discard v1's original conventions (license, no-telemetry, no-signing, etc.), which all still apply.

## What this update is

v1.5 ships an actual fix for the flagship LegacySupport bug: on ancient Intel-iGPU hardware (Ivy Bridge-era HD 2500/HD 4000 family), Minecraft 26.2 renders lava/water/portals as fully invisible and some blocks as fully black. v1 shipped without this fix; v1.5 delivers it based on founder-led root-cause research (see Masterdoc §2). **Version label: `Velofine 1.5 MC 26.2`.**

## How to work on this update

- **Extend the existing v1 LegacySupport module in place.** Don't rewrite it. If the new detection/registry system doesn't fit the existing structure cleanly, say so explicitly rather than silently restructuring broadly.
- **v1.5 is scoped to LegacySupport + updater/diagnostic tooling only.** Do not touch Optimus or Utility — broader Optimus work is v2, out of scope here.
- **Development is happening blind.** No one on the project has direct access to the affected hardware. The diagnostic export tool (Phase 1) and the tester feedback loop are the actual source of truth — prioritize getting real data over theorizing further from shader source alone. When implementing the shader fix in Phase 4, treat the root-cause explanation in the Masterdoc as a working hypothesis informed by strong circumstantial evidence, not a confirmed diagnosis — validate against real diagnostic reports as they come in.
- **Confidence-tiered fixes matter.** The two verified machines (i3-3110M/HD 4000 + Intel driver 15.33.53.5161; i5-3470S/HD 2500 + Windows-provided driver) get the full targeted shader-patch fix. Broader Ivy Bridge-family matches get only the conservative compatibility-renderer fallback until more field data comes in. Don't apply the aggressive fix to unverified hardware.
- **Everything here ships behind the "Experimental Legacy Fix" toggle**, opt-in for this release (not auto-enabled by default), offered both at install time (if hardware matches) and as an in-game settings toggle.

## Technical specifics

- **Corrected shaders are swappable asset files** (patched `.fsh`/`.vsh` replacing `rendertype_translucent`, `rendertype_end_portal`, `rendertype_solid`, `rendertype_cutout`), not compiled into the agent. This keeps future fix updates patchable without a full app rebuild. Java-side GL-call interception is a fallback only, for cases where the root cause turns out to be buffer setup rather than the shader itself.
- **General shader-robustness improvements apply globally**, regardless of detected hardware: defensive uniform/buffer fallback values, avoiding dynamic (non-constant) array indexing in fragment shaders, universal `GL_DEBUG_OUTPUT`/`KHR_debug`.
- **Detection is two-layer:** pre-context WMI/DXGI (Windows) for early UX (install-time toggle suggestion), post-context `glGetString` confirmation as the actual gate before applying any shader swap — protects against hybrid/switchable-graphics mismatches.
- **No telemetry, still.** `diagnostic.exe` is manual and user-triggered only — it never runs automatically or phones home, and it must not depend on Velofine being installed at all. Output is timestamped JSON, saved locally; the user hands the file to the founder manually. Do not build any automatic submission path in v1.5.
- **`diagnostic.exe` is a standalone monorepo module, not a Velofine feature.** Portable single-file `.exe`, simple GUI, its own independent version number. It asks for the user's Minecraft directory (not Velofine's) to extract the real `rendertype_*` shaders, then actually attempts to compile them via a minimal LWJGL-created OpenGL context, capturing real `GL_COMPILE_STATUS`/info-log output. Build its dual mode (baseline diagnosis + testing candidate fixed shaders sent later during Phase 4) from the start — it's the mechanism the whole Phase 4 tester feedback loop runs on. Bundle it as an extra file in the same release as the main installer.
- **Updater safety:** download → validate → atomic replace via staged temp path; snapshot the previous version and auto-restore only on hard failure (crash/won't launch). Softer regressions are handled by a manual "revert to previous version" button, not auto-rollback — don't try to have the updater infer "this looks visually wrong" on its own.
- **No code signing, still unsigned** — same v1 constraint carries forward.

## Testing

- The founder's friend (owner of the i3-3110M/HD 4000 reference machine) and additional testers are the real test environment — there is no CI-based way to validate the actual fix. Structure changes so a non-developer tester can meaningfully verify results (clear before/after instructions: what to check, what the diagnostic tool should now report).
- Standard CI (build/package) should still pass on every push regardless of hardware-fix validation status.
- No public GitHub issue template for diagnostic submissions yet — that's deferred until after the tester-first rollout phase.

## Definition of done for this update

The two verified reference machines (i3-3110M/HD 4000, i5-3470S/HD 2500) render lava, water, portals, and previously-black blocks correctly with the Experimental Legacy Fix toggle enabled, with no regression versus the pre-fix baseline. Broader family compatibility is a bonus, not a blocker.
